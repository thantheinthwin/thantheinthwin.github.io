If you're building software that needs to talk to the internet, you need to
master REST (Representational State Transfer). This isn't just a technical
acronym; it's the fundamental architectural style behind how modern web
services are built. A well-designed REST API is easy for other developers to
use and keeps your system efficient and stable by organizing everything
around simple, conceptual resources.

## 1. The Core Principle: Resources, Not Actions

The most fundamental rule of RESTful design is to structure your API around
**resources**. A resource is any conceptual entity that can be identified
and acted upon. Think of resources as **nouns, not verbs**.

- **Bad endpoint example:** `/getAllUsers` or `/createNewOrder` — the verb
  is baked into the URL.
- **Good endpoint example:** `/users` or `/orders/{id}` — just the noun.

The actions (the verbs) are implied by the standard HTTP methods themselves.

## 2. Structuring Your Endpoints: Naming Conventions

The URI (Uniform Resource Identifier) for a resource should clearly
identify the resource you are interacting with.

| Principle                 | Guideline                                                              | Example(s)                              |
| ------------------------- | ---------------------------------------------------------------------- | --------------------------------------- |
| Use plural nouns          | Name collections with plural nouns for consistency.                    | `/users`, not `/user`                   |
| Identify specific resources | Use a unique identifier in the path to address one item.             | `/users/123`                            |
| Model relationships       | Use nesting to show ownership — but keep it shallow.                   | `/users/123/orders`                     |
| Avoid verbs               | Never put action words in the URL; rely on the HTTP method instead.    | `GET /users`, not `/getAllUsers`        |


### 3.1. Verbs of the Web

The standard HTTP methods are used to perform the basic CRUD (Create, Read,
Update, Delete) operations on your resources. They provide the action part
of your request, so it never has to live in the URL.

| HTTP Method | Operation | Description                                                    | Example Endpoint & Action        |
| ----------- | --------- | -------------------------------------------------------------- | -------------------------------- |
| `GET`       | Read      | Retrieves a resource or a collection of resources.              | `GET /orders` — list orders      |
| `POST`      | Create    | Creates a new resource within a collection.                     | `POST /orders` — create an order |
| `PUT`       | Update    | Replaces an entire existing resource with the request payload.  | `PUT /orders/42` — replace       |
| `PATCH`     | Update    | Applies a partial update to an existing resource.               | `PATCH /orders/42` — modify      |
| `DELETE`    | Delete    | Removes a resource from the system.                             | `DELETE /orders/42` — remove     |

### 3.2. API Versioning

APIs inevitably change. Use versioning to prevent breaking existing
clients. The recommended approach is **URI versioning**.

- **Example:** `/v1/products` or `/v2/products`

### 3.3. Standard HTTP Status Codes

Status codes are crucial for signaling the outcome of a request. Using them
correctly is mandatory for a RESTful API.

| Category           | Key Codes & Meaning                                        | Common Use Cases                                          |
| ------------------ | ---------------------------------------------------------- | --------------------------------------------------------- |
| Success (2xx)      | `200 OK`, `201 Created`, `204 No Content`                  | Successful reads, successful creation, successful deletes |
| Client Error (4xx) | `400 Bad Request`, `401 Unauthorized`, `404 Not Found`     | Malformed input, missing authentication, missing resource |
| Server Error (5xx) | `500 Internal Server Error`, `503 Service Unavailable`     | Something went wrong on the server side, not the client's |

### 3.4. Data Format and Content Negotiation

JSON (JavaScript Object Notation) is the industry standard for data transfer.

- **Request:** specify the format being sent via the `Content-Type` header
  (e.g. `Content-Type: application/json`).
- **Response:** clients can request a format via the `Accept` header.

### 3.5. Statelessness

REST implies that the API be stateless. Every request must contain all the
information needed to process it. The server does not store any session
state information derived from previous requests. This improves reliability
and scalability.

### 3.6. Filtering, Sorting, and Pagination

For managing large collections of resources (e.g. `GET /products`), the key
query parameters are:

- **Pagination:** `GET /products?page=2&limit=25`
- **Filtering:** `GET /products?category=electronics&in_stock=true`
- **Sorting:** `GET /products?sort=-price`

By embracing the principles of resource orientation and leveraging the
power of HTTP methods, you can design RESTful APIs that are clean,
consistent, and a pleasure for developers to use.
